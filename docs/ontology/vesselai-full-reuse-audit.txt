SECTION 1 -- CURRENT TWINSHIP IMPORT CLOSURE
================================================================================

1. What does twinship-core.ttl currently import?

   twinship-core.ttl contains exactly these owl:imports statements:

     owl:imports <https://twin-ship.eu/twinship/vessel>
     owl:imports <https://twin-ship.eu/twinship/weather-conditions>
     owl:imports <https://twin-ship.eu/twinship/operational-modes>
     owl:imports <https://twin-ship.eu/twinship/operational-context>

   It does NOT directly import twinship-base. The base is pulled in
   transitively: each of the four modules listed above imports
   <https://twin-ship.eu/twinship/base>.

2. Do any current TwinShip modules import VesselAI directly?

   YES -- CRITICAL FINDING.

   twinship-base.ttl contains the following owl:imports statement:

     owl:imports <http://www.vesselAI-project.eu/vesselai> ;

   This is an actual owl:imports triple, not a comment. Because every
   TwinShip module imports twinship-base, this means VesselAI is
   transitively in the import closure of ALL current TwinShip modules
   including vessel.ttl, weather-conditions.ttl, operational-modes.ttl,
   and operational-context.ttl.

   The IRI <http://www.vesselAI-project.eu/vesselai> is mapped in
   model/catalog-v001.xml to external/vesselai/vesselAI_ontology_v2.owl.

3. Do any current TwinShip modules import DUL directly?

   No TwinShip TTL source file contains a direct owl:imports for DUL.
   However, vesselAI_ontology_v2.owl imports DUL:

     owl:imports <http://www.ontologydesignpatterns.org/ont/dul/DUL.owl#>

   Because twinship-base.ttl imports VesselAI (see point 2 above), DUL
   is in the TRANSITIVE import closure of TwinShip if a reasoner or
   tool follows owl:imports chains. Whether DUL is actually loaded
   depends on whether the reasoner resolves that external URI. There is
   no local catalog entry for DUL.

4. Do any current TwinShip modules import GeoSPARQL directly?

   No. Same reasoning as DUL -- GeoSPARQL is imported by VesselAI:

     owl:imports <http://www.opengis.net/ont/geosparql#>

   No local catalog entry exists for GeoSPARQL.

5. Do any current TwinShip modules import OWL-Time directly?

   No. Same reasoning -- OWL-Time is imported by VesselAI:

     owl:imports <http://www.w3.org/2006/time#>

   No local catalog entry exists for OWL-Time.

6. Does catalog-v001.xml contain VesselAI mappings?

   Yes. model/catalog-v001.xml contains:

     <uri id="VesselAI"
          name="http://www.vesselAI-project.eu/vesselai"
          uri="external/vesselai/vesselAI_ontology_v2.owl"/>

   There is also a duplicate entry inside a <group> block:

     <uri id="Automatically generated entry, Timestamp=1770135896276"
          name="http://www.vesselAI-project.eu/vesselai"
          uri="external/vesselai/vesselAI_ontology_v2.owl"/>

   model/external/vesselai/catalog-v001.xml contains a separate mapping:

     name="http://www.vesselAI-project.eu/ontology"
     uri="vesselAI_ontology_v2.owl"

   Note: this sub-catalog maps the TERM namespace IRI, not the ontology
   IRI -- these two differ (see Section 2 point 12 below).

7. Are those VesselAI mappings actually used by owl:imports?

   Yes. The owl:imports statement in twinship-base.ttl references the
   exact IRI <http://www.vesselAI-project.eu/vesselai> which is mapped
   in catalog-v001.xml. Whether a given tool follows this chain depends
   on whether the tool honours the OASIS XML Catalog file.

8. Is VesselAI currently in the TwinShip import closure?

   YES, by virtue of the owl:imports statement in twinship-base.ttl.
   This is an active import, not a comment or documentation mention.

   This contradicts the CLAUDE.md documentation, which states:
   "Do NOT import VesselAI into any TwinShip module" and describes
   VesselAI files as being in external/ for inspection/reference only.
   The owl:imports in twinship-base.ttl is an active divergence from
   the stated architectural intent.

9. Is DUL currently in the TwinShip import closure?

   YES, transitively via twinship-base.ttl -> VesselAI -> DUL.
   Tools that follow owl:imports chains (e.g., Protege, OWL reasoners)
   will attempt to load DUL, and will also attempt to load GeoSPARQL
   and OWL-Time if DUL or VesselAI external URIs are followed.
   There are no local catalog entries for DUL, GeoSPARQL, or OWL-Time,
   so attempts to resolve them will either fail or fetch them from the
   network.

10. Are there stale references to older module names?

    No stale references were found in any source TTL file to:
    - weatherconditions (old module name)
    - operations.ttl
    - draft-trim-mode.ttl
    - draft_time_mode.ttl
    - draft_trim_mode.ttl

    All current module imports in twinship-core.ttl reference only the
    canonical IRIs:
      <https://twin-ship.eu/twinship/vessel>
      <https://twin-ship.eu/twinship/weather-conditions>
      <https://twin-ship.eu/twinship/operational-modes>
      <https://twin-ship.eu/twinship/operational-context>

    The CLAUDE.md documentation mentions the old filenames as
    "do not create or reference" warnings, which is correct and current.

SUMMARY OF SECTION 1:

  The single most important finding in this section is that
  twinship-base.ttl currently contains an active owl:imports for
  VesselAI. This means DUL, GeoSPARQL, and OWL-Time are in the
  transitive import closure. This contradicts the stated IDO-only
  architecture. Whether this causes problems in practice depends on
  which tools are used and whether they follow external URI chains.
  This import should be removed as part of any cleanup action.

SECTION 2 -- FULL VESSELAI ONTOLOGY OVERVIEW
================================================================================

1. Main ontology IRI:

   http://www.vesselAI-project.eu/vesselai

   Declared in: vesselAI_ontology_v2.owl as owl:Ontology rdf:about=

2. Namespace used for classes and properties:

   http://www.vesselAI-project.eu/ontology#

   This is DIFFERENT from the ontology IRI. The ontology IRI uses the
   path segment "vesselai", while the term namespace uses "ontology#".
   This is an inconsistency in the VesselAI design. All class and
   property IRIs use the ontology# namespace, not the vesselai namespace.
   Example: :Vessel = http://www.vesselAI-project.eu/ontology#Vessel

3. Imported ontologies:

   a. DUL (DOLCE Ultralight):
      http://www.ontologydesignpatterns.org/ont/dul/DUL.owl#
   b. GeoSPARQL:
      http://www.opengis.net/ont/geosparql#
   c. OWL-Time:
      http://www.w3.org/2006/time#

   All three are imported in vesselAI_ontology_v2.owl and in main.ttl.
   They are NOT locally available in the TwinShip repository (no catalog
   entries for them in model/catalog-v001.xml). Resolving them requires
   network access or additional catalog configuration.

4. Top ontology used:

   DUL (DOLCE Ultralight). All major VesselAI classes root in DUL:
   - dul:Agent  (MovingObject -> Vessel)
   - dul:Region (Trajectory, TrajectoryPart, Route, RouteSegment)
   - dul:Event  (Event -> Environmental -> WeatherCondition)
   - dul:PhysicalPlace (Place -> Port)
   - dul:InformationEntity (CO2_emissionReport, MooringReport,
                            RouteAvailability)
   - dul:Object (Cargo)

   This is fundamentally different from TwinShip's use of IDO / ISO
   15926-14 as the upper ontology.

5. Main files / modules:

   File                              Role
   --------------------------------- -----------------------------------
   vesselAI_ontology_v2.owl          Main aggregate OWL file; declares
                                     the ontology IRI; imports DUL,
                                     GeoSPARQL, OWL-Time; contains

                                     WeatherPhenomena vocabulary (WMO)

8. Main data properties (VesselAI namespace):

   All VesselAI numeric/measurement properties are declared with
   rdfs:range xsd:string (not xsd:decimal or other numeric types).
   This is a significant data modelling weakness.

   Weather-specific "data properties" are declared as object properties
   with range xsd:string (also wrong -- these should be data properties).

   Emission-report properties on CO2_emissionReport all use xsd:string.

   Examples of weather object properties (all declared with
   rdfs:range xsd:string, which is incorrect for measurements):
   - 10_metre_U_wind_component_surface
   - 10_metre_V_wind_component_surface
   - 2_metre_temperature_surface
   - 2_metre_dewpoint_temperature_surface
   - Mean_sea_level_pressure_surface
   - Mean_wave_direction_msl
   - Mean_wave_period_msl
   - Sea_surface_temperature_surface
   - Total_precipitation_surface_1_Hour_Accumulation

   hasTimeStart, hasTimeEnd on time:TemporalEntity: rdfs:range xsd:string

9. Main individuals:

   VesselAI defines a large WMO weather phenomena vocabulary as
   named individuals (several hundred individuals) of class WeatherPhenomena,
   using codes from http://codes.wmo.int/306/4678/ as IRIs:
   - FZRA, FG, SN, RA, HZ, DS, SS, FZFG, etc.
   These are the only named individuals in VesselAI (aside from vessel
   type sets/enumerations). No individuals for vessel instances.

10. External dependencies:

    DUL (DOLCE Ultralight)    -- top ontology, pervasive
    GeoSPARQL                 -- for geometry (ogc:Geometry)
    OWL-Time                  -- for temporal features (time:TemporalEntity)

    All three are mandatory for VesselAI semantics to be complete.
    None of them are stored locally in the TwinShip repository.
    None of them have catalog entries in model/catalog-v001.xml.

    TrajectoryCluster        subClassOf dul:Region
    Route                    subClassOf dul:Region
    RouteSegment             subClassOf dul:Region
    CO2_emissionReport       subClassOf dul:InformationEntity
    MooringReport            subClassOf dul:InformationEntity
    RouteAvailability        subClassOf dul:InformationEntity

    WeatherCondition         subClassOf VesselAI:Event -> dul:Event

    hasPart                  subPropertyOf dul:hasPart

    Summary: ALL major VesselAI classes are DUL-dependent either
    directly or through the class hierarchy. There is no VesselAI class
    that can be extracted without either retaining a DUL reference or
    effectively redefining it from scratch.

12. Namespace inconsistency:

    Ontology IRI:   http://www.vesselAI-project.eu/vesselai
    Term namespace: http://www.vesselAI-project.eu/ontology#

    These are different. A tool importing the ontology by the ontology
    IRI obtains term definitions that use a different base IRI.
    TwinShip's catalog and base.ttl correctly use the ontology IRI.
    The VesselAI sub-catalog (external/vesselai/catalog-v001.xml)
    maps the term namespace IRI to the same OWL file. Both entries
    are needed if both IRIs are used as identifiers.

SECTION 3 -- VESSELAI DOMAIN COVERAGE BY AREA
================================================================================

A. VESSEL AND VESSEL CHARACTERISTICS
-------------------------------------

Classes:
  Vessel, MovingObject (~100+ vessel-type subclasses including
  Tanker, Ferry, BulkCarrier, Cargo_Vessel, Passenger_Vessel,
  Fishing_Vessel, Tug_Vessel, Special_Craft, Dredger_Vessel,
  Military_Ops, Ro-Ro_Passenger_Ship, etc.)

Object properties (on Vessel / MovingObject):
  hasIMO, hasCallsign, hasGrossTn, hasDeadWeight, hasActualHeight,
  hasCountryFlag, hasBuiltDate, hasLength, hasWidth, hasHeight,
  hasTrajectory, MMSIinstalledOnVessel (via Transcoder)

Data properties: None (all declared as object properties with range
  xsd:string -- a design weakness)

External dependencies: DUL (MovingObject subClassOf dul:Agent)

Useful for TwinShip? Partly.
  - The top-level vessel type taxonomy (Tanker, RoPax/Ro-Ro_Passenger_Ship,
    BulkCarrier, etc.) is useful as a reference for extending TwinShip's
    VesselSystem subclasses.
  - The AIS-derived vessel identification properties (hasIMO, hasCallsign,
    hasGrossTn, etc.) are potentially relevant.
  - TwinShip already has VesselSystem, RoRo, RoPax, Tanker in vessel.ttl.

TwinShip already covers? Partially.
  - VesselSystem (TwinShip) vs Vessel (VesselAI): similar concept,
    different upper class (TwinShipInanimatePhysicalObject vs dul:Agent).
  - RoRo, RoPax, Tanker exist in TwinShip.

Semantics compatible? NO for direct reuse.
  VesselAI Vessel is a subClassOf MovingObject subClassOf dul:Agent.
  TwinShip VesselSystem is a subClassOf TwinShipInanimatePhysicalObject
  subClassOf ido:InanimatePhysicalObject.
  dul:Agent and ido:InanimatePhysicalObject are not equivalent.
  A vessel is a physical object in IDO, not an "agent" in the cognitive
  sense. The VesselAI modeling choice to root Vessel in dul:Agent is
  designed for trajectory/movement analysis, not the physical twin
  perspective of TwinShip.

Recommendation:
  - Use rdfs:seeAlso annotations on TwinShip Vessel/type classes to
    reference VesselAI vessel types for traceability.
  - Do not use skos:closeMatch or owl:equivalentClass.
  - The vessel type taxonomy (Tanker, Ferry, etc.) labels are useful
    for extending TwinShip VesselSystem subclasses natively.
  - VesselAI vessel property labels (hasIMO, hasGrossTn, etc.) are
    useful as naming inspiration for TwinShip vessel data properties.


B. ENGINE, MACHINERY, PROPULSION, POWER, FUEL, EQUIPMENT
----------------------------------------------------------

Classes: None.
  VesselAI has NO engine, propulsion, fuel, or machinery classes at all.
  The vessel is treated as a black box for movement and reporting.
  There is a Cargo class hierarchy (UN class 1-9 dangerous goods) and
  a Bunker class (fuel storage, but modelled as a vessel type not a
  system), but nothing about engine systems.

Object properties: None specific to propulsion.

Data properties: Fuel consumption is modelled only at the report level
  on CO2_emissionReport (reportedFuelConsumption etc.) -- not at the
  system level.

External dependencies: None specific to this area.

Useful for TwinShip? NO.
  TwinShip has detailed engine/propulsion coverage in vessel.ttl
  (MainEngineSystem, AuxiliaryEngineSystem, PropellerSystem,
  GearboxSystem, ShaftGeneratorSystem, Boiler, Fuel, DieselEngine,
  FourStroke, CPP, FPP, etc.). VesselAI contributes nothing here.

Recommendation: Ignore. VesselAI has no content in this area.


C. VOYAGE, TRIP, ROUTE, TRAJECTORY, MOVEMENT, NAVIGATION
----------------------------------------------------------

Classes:
  Trajectory (and subclasses: ActualTrajectory, IntendedTrajectory,
  RegulatedTrajectory, SyntheticTrajectory, DangerousTrajectory,
  OpenTrajectory, ClosedTrajectory)
  TrajectoryPart (Node, RawPosition, Segment)
  TrajectoryCluster
  Route (subClassOf dul:Region; MarineRoute, NationalFerryLine,
  InternationalFerryLine)
  RouteSegment (subClassOf dul:Region)
  RouteAvailability (subClassOf dul:InformationEntity)

Object properties:
  hasTrajectory, hasStart, hasEnd, comprises, hasPart,
  hasCourseOverGround, hasHeading, hasNavigationalStatus,
  hasSpeedOverGround, hasGeometry (-> ogc:Geometry),
  hasTemporalFeature (-> time:TemporalEntity),
  hasTimeStart, hasTimeEnd, ofMovingObject

Data properties: None (all xsd:string object properties).

External dependencies:
  DUL (Trajectory, TrajectoryPart, Route all subClassOf dul:Region)
  GeoSPARQL (hasGeometry range ogc:Geometry)
  OWL-Time (hasTemporalFeature range time:TemporalEntity)

Useful for TwinShip? Partially for labels/concepts, not for reuse.
  VesselAI's Trajectory concept is different from TwinShip's Voyage/
  VoyageLeg. Trajectory is a spatial-temporal track of AIS positions
  (a dul:Region). Voyage in TwinShip is a process (ido:Activity-based).
  Route in VesselAI is a dul:Region (geographic path). Route in TwinShip
  is a TwinShipInformationObject (planned route data). These are
  semantically related but not equivalent.

TwinShip already covers?
  - Voyage, VoyageLeg in operational-context.ttl (TwinShipProcess)
  - Route in operational-context.ttl (TwinShipInformationObject)
  - hasDeparturePort, hasArrivalPort, followsRoute, hasVoyage,
    hasVoyageLeg defined natively

Semantics compatible? NO for direct reuse.
  VesselAI Trajectory/Route are dul:Region (spatial regions).
  TwinShip Voyage/VoyageLeg are TwinShipProcess (ido:Activity).
  These represent fundamentally different ontological categories.

Recommendation:
  - rdfs:seeAlso annotations on Voyage/VoyageLeg to VesselAI Trajectory
    for traceability.
  - Do not reuse or import VesselAI trajectory classes.
  - A future TwinShip trajectory module (for AIS-style position data)
    could independently define a Trajectory class rooted in IDO without
    needing VesselAI.


D. EVENTS, ACTIVITIES, STATES, AND SITUATIONS
-----------------------------------------------

Classes:
  Event (subClassOf dul:Event)
  Environmental (subClassOf Event)
  WeatherCondition (subClassOf Environmental, Dynamic)
  LowLevel (subClassOf Event)
  MaritimeLowLevelEvent (subClassOf LowLevel)
  Dynamic (implied by WeatherCondition rdfs:subClassOf :Dynamic --
  but :Dynamic is not explicitly defined in inspected files)

Object properties:
  occurs, occursAt, triggers, affectedBy, affects, hasReferencePosition,
  hasReferenceTime

External dependencies:
  DUL (Event subClassOf dul:Event)
  GeoSPARQL (hasReferencePosition range ogc:Geometry)
  OWL-Time (hasReferenceTime range time:TemporalEntity)

Useful for TwinShip? No for direct reuse.
  WeatherCondition as a dul:Event is semantically incompatible with
  TwinShip WeatherCondition as a TwinShipQuality.
  TwinShip has TwinShipEvent (subClassOf ido:Event) for discrete events.

TwinShip already covers?
  - WeatherCondition, WindCondition in weather-conditions.ttl
  - TwinShipEvent in twinship-base.ttl (for future event modelling)
  - OperatingState, EngineMode, etc. in operational-modes.ttl

Recommendation:
  - rdfs:seeAlso only, already implemented in weather-conditions.ttl.
  - Do not import or reuse VesselAI event classes.


E. WEATHER, ENVIRONMENTAL CONDITIONS, CONTEXTUAL INFORMATION
-------------------------------------------------------------

Classes:
  WeatherCondition (subClassOf Environmental -> Event -> dul:Event)
  WeatherPhenomena (large WMO code vocabulary as individuals)

Object properties (all with range xsd:string -- incorrect for numerics):
  10_metre_U_wind_component_surface
  10_metre_V_wind_component_surface
  2_metre_temperature_surface
  2_metre_dewpoint_temperature_surface
  Mean_sea_level_pressure_surface
  Mean_wave_direction_msl
  Mean_wave_period_msl
  Sea_surface_temperature_surface
  Total_precipitation_surface_1_Hour_Accumulation
  hasWeatherCondition (domain TrajectoryPart)
  hasWeatherPhenomena (range WeatherPhenomena)

External dependencies:
  DUL (WeatherCondition -> dul:Event)
  OWL-Time (hasReferenceTime on Event)
  GeoSPARQL (hasReferencePosition on Event)

Useful for TwinShip? Partially (the ERA5/GFS weather variable names).
  The specific weather parameter names (U/V wind components, wave
  direction, wave period, sea surface temperature, precipitation) are
  relevant as the same ERA5/GFS variables are commonly used in vessel
  performance analysis. These labels can inform TwinShip weather data
  property naming.

TwinShip already covers?
  - WeatherCondition, WindCondition in weather-conditions.ttl
  - windSpeed, windDirection data properties

TwinShip missing but potentially relevant:
  - Sea surface temperature
  - Wave height and period
  - Significant wave height
  - Air pressure
  - Precipitation
  These can be added to weather-conditions.ttl as native TwinShip
  data properties without any VesselAI dependency.

Semantics compatible? NO.
  VesselAI WeatherCondition is a dul:Event.
  TwinShip WeatherCondition is a TwinShipQuality.
  These are incompatible upper classes.

WMO WeatherPhenomena vocabulary:
  VesselAI events.ttl includes several hundred named individuals
  representing WMO code table 4678 weather phenomena. These use
  http://codes.wmo.int/ IRIs directly, which means the actual terms
  are WMO-registered vocabulary, not VesselAI-specific. TwinShip can
  reference WMO codes directly without VesselAI.

Recommendation:
  - rdfs:seeAlso only (already done for WeatherCondition,
    10_metre_U/V_wind_component in weather-conditions.ttl).
  - Extend TwinShip weather-conditions.ttl with additional native
    data properties for sea state, wave, and pressure variables.
  - Reference WMO code table 4678 directly if a weather phenomena
    vocabulary is needed.


F. GEOSPATIAL, GEOMETRY, AND LOCATION
---------------------------------------

Classes: None (VesselAI uses GeoSPARQL ogc:Geometry directly).
Object properties:
  hasGeometry (subPropertyOf dul:hasConstituent; range ogc:Geometry)

================================================================================
SECTION 5 -- SEMANTIC COMPATIBILITY ANALYSIS
================================================================================

For each key candidate:

------------------------------------------------------------------------------
CANDIDATE 1: WeatherCondition
------------------------------------------------------------------------------

VesselAI meaning: A weather event occurring at a trajectory position.
  Modelled as a subclass of Environmental -> Event -> dul:Event.
  It is a temporal occurrence, not a quality or state.

TwinShip meaning: An environmental quality describing weather conditions.
  Modelled as a subclass of TwinShipQuality -> ido:Quality.
  It is a quality attributed to a physical situation, not an event.

VesselAI type: dul:Event (via Event -> Environmental -> WeatherCondition)
TwinShip type: TwinShipQuality (-> ido:Quality)

Compatible? NO.
  dul:Event and ido:Quality are categorially different.
  An OWL reasoner would not classify TwinShip WeatherCondition
  individuals as VesselAI WeatherCondition instances.

Would extraction preserve semantics? NO.
  To extract without DUL, WeatherCondition would need a new superclass.
  Its semantics (temporal occurrence at a position) would need to be
  abandoned or replaced, at which point it is effectively redefined.

Would extraction redefine the concept? YES.
  Removing dul:Event from the hierarchy fundamentally changes what the
  class asserts.

rdfs:seeAlso safe? YES -- already implemented in weather-conditions.ttl.
skos:relatedMatch safe? YES (related concept in same domain).
skos:closeMatch safe? NO -- the superclasses are categorially different.
owl:equivalentClass safe? NO -- incompatible superclasses.

------------------------------------------------------------------------------
CANDIDATE 2: Vessel vs VesselSystem
------------------------------------------------------------------------------

VesselAI meaning: A moving object with floating capabilities.
  Modelled as subClassOf MovingObject subClassOf dul:Agent.
  dul:Agent implies agency and intentionality.

TwinShip meaning: A maritime vessel as a physical artefact.
  Modelled as subClassOf TwinShipInanimatePhysicalObject
  subClassOf ido:InanimatePhysicalObject.
  ido:InanimatePhysicalObject implies a physical thing without agency.

VesselAI type: dul:Agent
TwinShip type: TwinShipInanimatePhysicalObject (ido:InanimatePhysicalObject)

Compatible? NO.
  Rooting a vessel in dul:Agent (usually for cognitive agents) is a
  modelling decision driven by VesselAI's focus on movement/tracking.
  TwinShip correctly models a vessel as an inanimate physical object.

rdfs:seeAlso safe? YES.
skos:relatedMatch safe? YES.
skos:closeMatch safe? Marginal -- the labels match but superclasses differ.
  Use skos:relatedMatch to be conservative.
owl:equivalentClass safe? NO.

------------------------------------------------------------------------------
CANDIDATE 3: Voyage vs Trajectory
------------------------------------------------------------------------------

VesselAI meaning: A spatial-temporal track of AIS positions.
  Trajectory is a dul:Region (a spatial region, not a process).

TwinShip meaning: A vessel operational process (port-to-port passage).
  Voyage is a TwinShipProcess (subClassOf ido:Activity).

VesselAI type: dul:Region
TwinShip type: TwinShipProcess (ido:Activity)

Compatible? NO -- fundamentally different categories.
  A region (spatial extent) is not a process (temporal activity).

rdfs:seeAlso safe? YES (conceptually related in the maritime domain).
skos:relatedMatch safe? YES.
skos:closeMatch safe? NO.
owl:equivalentClass safe? NO.

------------------------------------------------------------------------------
CANDIDATE 4: Route (TwinShip) vs Route (VesselAI)
------------------------------------------------------------------------------

VesselAI meaning: A geographic course between two locations.
  Modelled as subClassOf dul:Region (a spatial region).

TwinShip meaning: Planned or observed route data.
  Modelled as TwinShipInformationObject (ido:InformationObject).

VesselAI type: dul:Region
TwinShip type: TwinShipInformationObject (ido:InformationObject)

Compatible? NO.
  A dul:Region is a spatial extent. An ido:InformationObject is
  a piece of information. These are different even though both can
  represent "a route". The modelling choice in TwinShip (route as
  information artefact) is intentional for the first release.

rdfs:seeAlso safe? YES.
skos:relatedMatch safe? YES.
skos:closeMatch safe? Marginal -- same label but different category.
owl:equivalentClass safe? NO.

------------------------------------------------------------------------------
CANDIDATE 5: FuelConsumptionSummary vs CO2_emissionReport
------------------------------------------------------------------------------

VesselAI meaning: A report capturing EU-MRV fuel and CO2 metrics.
  Modelled as subClassOf dul:InformationEntity.
  All values typed as xsd:string.

TwinShip meaning: Derived or aggregated fuel consumption summary.
  Modelled as TwinShipInformationObject (ido:InformationObject).
  Values use xsd:decimal.

VesselAI type: dul:InformationEntity
TwinShip type: TwinShipInformationObject (ido:InformationObject)

Compatible? Conceptually related but superclasses differ.
  ido:InformationObject and dul:InformationEntity are not equivalent
  but are both information categories. Semantically closer than the
  dul:Event vs ido:Quality case.

rdfs:seeAlso safe? YES.
skos:relatedMatch safe? YES.
skos:closeMatch safe? Borderline -- conceptually close, different superclass.
  Use skos:relatedMatch to be conservative.
owl:equivalentClass safe? NO.

------------------------------------------------------------------------------
CANDIDATE 6: Port (TwinShip) vs Port (VesselAI)
------------------------------------------------------------------------------

VesselAI meaning: A physical port location (dul:PhysicalPlace).
  With UNLOCODE and port feature properties. Many port type subclasses.

TwinShip meaning: A port identifier/code (TwinShipInformationObject).
  Pragmatic first-release modelling.

Compatible? NO -- physical place vs information object.
  Same label, same domain, but different ontological category.

rdfs:seeAlso safe? YES.
skos:relatedMatch safe? YES.
skos:closeMatch safe? NO -- different categories.
owl:equivalentClass safe? NO.

------------------------------------------------------------------------------
CANDIDATE 7: VesselAI RoPax / Ro-Ro_Passenger_Ship vs TwinShip RoPax
------------------------------------------------------------------------------

VesselAI: Ro-Ro_Passenger_Ship subClassOf Passenger_Vessel subClassOf Vessel
  (dul:Agent)
TwinShip: RoPax subClassOf VesselSystem
  (ido:InanimatePhysicalObject)

Compatible? Same real-world concept; different upper class.
  At the vessel type label level, these refer to the same type of ship.

rdfs:seeAlso safe? YES.
skos:relatedMatch safe? YES.
skos:closeMatch safe? Acceptable at the domain level despite different
  upper classes -- the label refers to the same vessel type.
  Use skos:relatedMatch to be conservative given the superclass mismatch.
owl:equivalentClass safe? NO -- different upper classes.

Same analysis applies to: RoRo / Ro-Ro_Cargo, Tanker / Tanker.

------------------------------------------------------------------------------
SUMMARY OF SECTION 5
------------------------------------------------------------------------------

No VesselAI term is semantically compatible enough with TwinShip to
justify owl:equivalentClass or owl:equivalentProperty assertions.

skos:closeMatch is UNSAFE for:
  WeatherCondition (dul:Event vs ido:Quality -- incompatible categories)
  Vessel / VesselSystem (dul:Agent vs ido:InanimatePhysicalObject)
  Trajectory / Voyage (dul:Region vs ido:Activity)
  Route (dul:Region vs ido:InformationObject)
  Port (dul:PhysicalPlace vs ido:InformationObject)

skos:relatedMatch is SAFE for all the above.

rdfs:seeAlso is safe universally (it is non-semantic).

The pattern is consistent: VesselAI is DUL-based, TwinShip is IDO-based.
These upper ontologies represent different philosophical commitments.
DUL categories (Agent, Region, Event, InformationEntity) do not map
cleanly onto IDO categories (InanimatePhysicalObject, Activity, Event,
Quality, InformationObject). Safe semantic mapping requires per-term
analysis; broad equivalence claims would be incorrect.

SECTION 6 -- SHOULD VesselAI-simplified.ttl BE CREATED?
================================================================================

Option A: Do not create VesselAI-simplified.ttl. Define needed concepts
          natively in TwinShip. Use rdfs:seeAlso annotations only.

Option B: Create VesselAI-simplified.ttl as a DUL-free vocabulary extract.
          Do not import it into core TwinShip modules.

Option C: Create VesselAI-simplified.ttl and import it from selected modules.

Option D: Keep importing full VesselAI.

Evaluation of each option:

OPTION A -- No simplified file
--------------------------------
Complexity:          LOW. No new file, no maintenance burden.
Maintainability:     HIGH. No external dependency to track.
Risk of DUL:         NONE. DUL cannot enter through a non-existent file.
Semantic compat.:    HIGH. TwinShip remains IDO-pure.
Value for users:     MODERATE. Users only see TwinShip-native terms.
                     VesselAI connection is documented via rdfs:seeAlso.
Query simplicity:    HIGH. No mixed namespace queries.
Documentation:       LOW burden. Explain that VesselAI is external ref.
Long-term arch.:     CLEAN. IDO-only commitment is maintained.
IDO alignment:       FULL. No second upper-ontology path.
Supports reuse goal: YES, in the sense that the investigation has been
                     done and the decision documented with evidence.
                     rdfs:seeAlso provides traceability.

OPTION B -- Simplified file, not imported
------------------------------------------
Complexity:          MODERATE. A new file to maintain; no functional
                     benefit unless imported somewhere.
Maintainability:     MODERATE. Must be kept in sync with VesselAI
                     updates; risk of bit-rot.
Risk of DUL:         LOW. File exists but is not imported. A future
                     developer could accidentally import it.
Semantic compat.:    PROBLEMATIC. Stripping DUL from VesselAI terms
                     effectively redefines them. The resulting file
                     would not represent VesselAI semantics faithfully.
                     It would be a new, underdefined vocabulary.
Value for users:     LOW. If it is not imported, it adds no value that
                     rdfs:seeAlso annotations cannot provide.
Query simplicity:    Unaffected (not imported).
Documentation:       MODERATE burden. Must explain what was stripped.
Long-term arch.:     AMBIGUOUS. File exists as a future temptation for
                     import.
IDO alignment:       MAINTAINED (if not imported).
Supports reuse goal: PARTIALLY. Provides a thin reference vocabulary
                     but without DUL it loses its semantic grounding
                     in VesselAI. Users cannot use VesselAI reasoners
                     against the simplified file.

OPTION C -- Simplified file, imported into modules
----------------------------------------------------
Complexity:          HIGH. Maintaining a DUL-free extract is ongoing work.
Maintainability:     LOW. VesselAI updates require re-stripping.
Risk of DUL:         MEDIUM TO HIGH. Any property in the simplified file
                     that subclasses or references a DUL concept will
                     reintroduce DUL if not carefully audited.
Semantic compat.:    PROBLEMATIC. As above -- stripping superclasses
                     redefines terms.
Value for users:     LOW. The DUL-free terms lose their place in the
                     VesselAI hierarchy and provide little additional
                     value over TwinShip-native equivalents.
Query simplicity:    LOW. Two term namespaces in one ontology is
                     confusing for SPARQL users.
Documentation:       HIGH burden.
Long-term arch.:     FRAGILE.
IDO alignment:       COMPROMISED unless very carefully managed.
Supports reuse goal: MARGINALLY. The goal was reuse; what is produced
                     is effectively new term definitions that can no
                     longer be used with VesselAI tools.

OPTION D -- Keep importing full VesselAI
------------------------------------------
Complexity:          HIGH. DUL, GeoSPARQL, OWL-Time all enter.
Maintainability:     LOW. External dependency on three large ontologies.
Risk of DUL:         CERTAIN. DUL is in the import closure already.
Semantic compat.:    INCOMPATIBLE. DUL and IDO are different foundations.
Value for users:     LOW. VesselAI adds confusion rather than value
                     given the semantic incompatibility.
Query simplicity:    LOW. Multiple upper ontologies in one graph.
Documentation:       HIGH burden.
Long-term arch.:     PROBLEMATIC.
IDO alignment:       BROKEN.
Supports reuse goal: NO. The owl:imports currently in twinship-base.ttl
                     is the evidence that Option D was attempted and
                     has introduced the exact architectural problem
                     the design decision is meant to resolve.

RECOMMENDED OPTION: A

Rationale: The evidence from this audit clearly shows that VesselAI
terms cannot be reused without retaining DUL semantics or effectively
redefining the terms. In either case, creating a simplified file adds
no benefit over native TwinShip definitions. rdfs:seeAlso annotations
satisfy the traceability goal without any semantic risk. Option A also
requires the removal of the existing owl:imports <VesselAI> statement
from twinship-base.ttl, which is the most urgent implementation action.

================================================================================
SECTION 8 -- IF VesselAI-simplified.ttl IS NOT RECOMMENDED
================================================================================

This section documents the decision NOT to create VesselAI-simplified.ttl.

1. Clear reasons why VesselAI-simplified.ttl is not recommended:

   a. DUL pervasiveness: Every major VesselAI class is either directly
      subClassOf a DUL class or transitively so. There is no non-trivial
      VesselAI class that can be extracted without either keeping a DUL
      reference (reintroducing the dependency) or removing the superclass
      (effectively redefining the term as something new).

   b. Semantic mismatch at upper-ontology level: DUL and IDO represent
      different ontological commitments. VesselAI terms inherit DUL
      semantics that are incompatible with IDO categories:
        - VesselAI:Vessel is a dul:Agent (IDO models vessels as
          InanimatePhysicalObjects)
        - VesselAI:WeatherCondition is a dul:Event (IDO models conditions
          as Qualities)
        - VesselAI:Trajectory is a dul:Region (TwinShip models voyages
          as Activities/Processes)
      No realistic extraction can bridge this without redefinition.

   c. TwinShip already covers the needed concepts natively and with
      better semantics (IDO-aligned, with proper OWL restriction patterns,
      and correct numeric datatypes). VesselAI adds no semantic value
      that TwinShip does not already provide or cannot provide natively.

   d. VesselAI measurement properties use xsd:string for all numeric
      values. This is a significant data quality issue. TwinShip correctly
      uses xsd:decimal / xsd:double for measurements. Reusing VesselAI
      measurement patterns would degrade TwinShip data quality.

   e. VesselAI has no coverage of engine/propulsion/machinery systems
      (the most detailed part of TwinShip's vessel.ttl). The intersection
      between VesselAI and TwinShip is too small to justify a dependency.

   f. Creating a simplified file and not importing it provides no
      functional benefit over rdfs:seeAlso annotations alone.

   g. Creating a simplified file and importing it would require ongoing
      maintenance as VesselAI evolves, with risk of reintroducing DUL.

2. VesselAI terms that SHOULD still be referenced with rdfs:seeAlso:

   Already implemented (in weather-conditions.ttl):
     :WeatherCondition rdfs:seeAlso
       <http://www.vesselAI-project.eu/ontology#WeatherCondition>
     :WindCondition rdfs:seeAlso
       <http://www.vesselAI-project.eu/ontology#10_metre_U_wind_component_surface>
     :WindCondition rdfs:seeAlso
       <http://www.vesselAI-project.eu/ontology#10_metre_V_wind_component_surface>

   Recommended for addition (see Section 9 mapping table for details):
     :VesselSystem  -> VesselAI:Vessel
     :RoPax         -> VesselAI:Ro-Ro_Passenger_Ship
     :RoRo          -> VesselAI:Ro-Ro_Cargo
     :Tanker        -> VesselAI:Tanker
     :Voyage        -> VesselAI:Trajectory
     :VoyageLeg     -> VesselAI:Segment (or TrajectoryPart)
     :Route         -> VesselAI:Route
     :Port          -> VesselAI:Port
     :FuelConsumptionSummary -> VesselAI:CO2_emissionReport

   The following statement should be added to CLAUDE.md (when updated)
   and to relevant README files:

   "VesselAI is not imported by any TwinShip module. The VesselAI
   files are retained in model/external/vesselai/ for inspection and
   reference only. Selected TwinShip terms reference VesselAI terms
   using non-semantic rdfs:seeAlso annotations for source traceability.
   No skos:closeMatch or owl:equivalentClass assertions to VesselAI
   terms are made because VesselAI is DUL-based and TwinShip is
   IDO-based; these upper ontologies represent incompatible
   ontological commitments. See docs/ontology/vesselai-full-reuse-audit.txt
   for the full design decision justification."

8. How this decision supports the IDO-only architecture:

   IDO (ISO 15926-14) provides a coherent set of top-level categories
   for the engineering and industrial domain. TwinShip's abstraction
   layer (TwinShipInanimatePhysicalObject, TwinShipProcess,
   TwinShipQuality, TwinShipInformationObject) maps cleanly onto IDO.
   VesselAI's DUL-based hierarchy would introduce a second top-level
   classification path, causing:
   - Potential reasoning conflicts (dul:Agent and ido:InanimatePhysical-
     Object are asserted to be the superclass of the same vessel)
   - SPARQL query complexity (two namespaces for the same domain)
   - Maintenance complexity (two upper ontologies to track)
   Removing the VesselAI import from twinship-base.ttl and keeping
   all TwinShip terms under the IDO hierarchy ensures a clean,
   single-root architecture.

9. How this decision satisfies the original reuse investigation goal:

   The original intent was to assess whether VesselAI could be reused.
   This audit has performed that assessment comprehensively and found
   that direct reuse is not semantically justified. The decision to
   NOT import VesselAI is an evidence-based design decision, not an
   arbitrary one. The audit documentation serves as the permanent
   justification for this architectural choice.

SECTION 10 -- QUDT, SIMPLE DATA PROPERTIES, AND QUANTITY VALUES
================================================================================

1. Whether VesselAI measurement properties are useful:

   NO in their current form. VesselAI declares all numeric and temporal
   measurements as owl:ObjectProperty with rdfs:range xsd:string. This
   is incorrect OWL design. Values that are measurements (speed,
   heading, temperature, fuel mass) should be xsd:decimal or appropriate
   numeric types, or should be modelled as data properties.

   Specific issues found:
   - hasSpeedOverGround: domain TrajectoryPart, range xsd:string
     (should be range xsd:decimal or qudt:Quantity)
   - hasCourseOverGround: range xsd:string (should be xsd:decimal in degrees)
   - hasHeading: range xsd:string (should be xsd:decimal)
   - 10_metre_U_wind_component_surface: range xsd:string (should be
     a numeric data property for m/s values)
   - reportedFuelConsumption: range xsd:string (should be xsd:decimal)
   - All CO2_emissionReport properties: range xsd:string

   These represent a clear design defect in VesselAI that TwinShip
   should NOT reproduce.

2. Whether VesselAI uses proper numeric datatypes:

   NO. All quantitative properties in VesselAI use rdfs:range xsd:string.
   TwinShip correctly uses xsd:decimal / xsd:double for measurements
   (e.g., windSpeed rdfs:range xsd:decimal; twShaftPowerMaxInKW
   rdfs:range xsd:double).

3. Whether TwinShip's current simple data properties are better:

   YES. TwinShip's current pattern (simple xsd:decimal / xsd:double
   data properties) is correct, SPARQL-friendly, and semantically
   adequate for first release. It avoids the xsd:string mistake in
   VesselAI and avoids the complexity of full QUDT quantity values.

4. Whether QUDT modelling should be added now or deferred:

   DEFER. QUDT quantity-value modelling (pairing a numeric value with
   a unit via qudt:Quantity / qudt:value / qudt:unit) adds significant
   complexity and is not required for the current TwinShip use cases
   (performance analysis, fuel consumption profiling). The current
   pattern of using xsd:decimal with unit convention documented in
   rdfs:comment is sufficient.

   The QUDT schema and vocabularies are already local
   (external/SCHEMA_QUDT-simplified.ttl, vocabularies/VOCAB_QUDT_UNIT2-
   simplified.ttl, vocabularies/VOCAB_QUDT-QUANTITY-KINDS-simplified.ttl)
   and imported in twinship-base.ttl, so a future QUDT upgrade path
   is available without requiring new imports.

5. Whether optional QUDT measurement modules are justified:

   Not for the current release. If in future TwinShip needs to support
   interoperability with systems that require explicit unit annotation,
   optional modules such as:
   - measurements-qudt.ttl
   - weather-qudt.ttl
   - vessel-qudt.ttl
   could be defined as optional extensions without modifying the core
   modules. This is the preferred extensibility approach.

6. Whether this affects the VesselAI-simplified.ttl decision:

   It reinforces Option A. VesselAI's measurement patterns are
   inferior to TwinShip's. Adopting any VesselAI measurement properties
   would regress TwinShip data quality from xsd:decimal to xsd:string.

SECTION 12 -- FINAL RECOMMENDATION
================================================================================

1. Recommended option: A

   Do not create VesselAI-simplified.ttl. Remove the existing VesselAI
   owl:imports from twinship-base.ttl. Continue developing TwinShip-
   native modules under the IDO-based abstraction layer. Use rdfs:seeAlso
   annotations only for source traceability.

2. Rationale:

   VesselAI is a well-structured domain ontology, but it is fundamentally
   DUL-based (DOLCE Ultralight) and its core classes cannot be extracted
   without either retaining DUL dependencies or effectively redefining
   the terms as something new. Every meaningful VesselAI class roots in
   dul:Agent, dul:Region, dul:Event, dul:PhysicalPlace, or
   dul:InformationEntity -- categories that are categorially different
   from the corresponding IDO classes used in TwinShip. VesselAI also
   uses xsd:string for all quantitative properties, which is a
   significant data quality defect compared to TwinShip's correct use
   of numeric datatypes. TwinShip already natively covers all the
   domains where VesselAI would have contributed terms (vessel types,
   weather conditions, voyage/leg structure, fuel consumption, modes
   and states) and does so with semantically superior IDO-aligned
   definitions. The traceability goal can be fully satisfied by
   rdfs:seeAlso annotations, which are already partially implemented
   in weather-conditions.ttl. Keeping VesselAI files in external/ as
   reference material preserves the investigation record without
   creating any import dependency.

3. Create VesselAI-simplified.ttl now: NO

4. Import VesselAI anywhere in TwinShip now: NO
   Additionally, the EXISTING owl:imports in twinship-base.ttl must
   be REMOVED as a priority action.

5. Keep VesselAI files in external/: YES
   They serve as audit evidence and design decision documentation.

6. Keep the VesselAI catalog entry: YES (with documentation comment)
   Once the owl:imports is removed, the entry is functionally unused.
   Keep it clearly marked as "external reference only" to prevent
   future inadvertent imports. Alternatively, remove after cleanup.

7. Use rdfs:seeAlso annotations: YES
   Already implemented in weather-conditions.ttl. Extend to vessel.ttl
   (VesselSystem, RoPax, RoRo, Tanker) as priority 2 actions.
   Optionally extend to operational-context.ttl (Voyage, Route, Port,
   FuelConsumptionSummary).

8. Use SKOS mappings: YES, but conservatively.
   skos:relatedMatch ONLY (not skos:closeMatch) for:
     :VesselSystem skos:relatedMatch VAI:Vessel
     :FuelConsumptionSummary skos:relatedMatch VAI:CO2_emissionReport
   All other candidate mappings should use rdfs:seeAlso only.
   NO skos:closeMatch assertions recommended for current release.

9. Use OWL equivalence: NO
   owl:equivalentClass and owl:equivalentProperty must not be used
   with any VesselAI term. All candidate VesselAI terms have incompatible
   upper-ontology superclasses with their TwinShip counterparts.
